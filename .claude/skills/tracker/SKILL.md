# Трекер цен по списку

## Назначение

Один прогон трекера — это обход всего списка отслеживаемых товаров, сборка
их цен в один JSON-массив, сравнение этого массива с предыдущим прогоном из
`tracker-data` и сохранение нового прогона как отдельный файл. Скилл сам не
извлекает цены — для каждого URL он вызывает уже готовый скилл
`extract-price` и переиспользует его результат. Не дублируй логику разбора
цены, скидки или рассрочки внутри этого скилла, и не переизобретай правила
значимости — они описаны в `KNOWLEDGE.md` в корне проекта.

## Алгоритм

### 1. Пройди список и сразу собери JSON-массив прогона

Заведи пустой массив прогона. Для каждого URL из списка выше вызови скилл
`extract-price` (инструмент `Skill`, `skill: "extract-price"`,
`args: "<url>"`), передав именно этот URL как есть, без изменений.

Обрабатывай товары **строго последовательно**, один за другим, а не
параллельно: `extract-price` может открывать браузерную вкладку, и
параллельные вызовы будут конкурировать за одну и ту же вкладку/сессию.

`extract-price` возвращает JSON-объект вида:

```json
{"regular_price": 19990, "sale_price": 16690, "has_credit": true}
```

Сразу добавь в массив прогона объект, дополнив этот ответ названием товара
и URL из списка — без промежуточной таблицы и без обратного парсинга:

```json
{"product": "<название товара>", "url": "<url>", "regular_price": 19990, "sale_price": 16690, "has_credit": true}
```

Если вызов для одного URL не удался или вернул ошибку — не прерывай весь
прогон. Добавь в массив объект для этого товара с `regular_price: null`,
`sale_price: null`, `has_credit: false` и переходи к следующему URL.

К концу шага у тебя есть один готовый JSON-массив — по одному объекту на
каждый URL из списка, в том же порядке. Он используется без изменений и для
сравнения с предыдущим прогоном (§2), и для сохранения (§4), и для показа
результата (§5).

### 2. Найди и прочитай предыдущий прогон

Сделай это **до** сохранения нового прогона (§4) — иначе сегодняшний файл
перезапишется раньше, чем ты успеешь с чем-то его сравнить.

1. Узнай сегодняшнюю дату в формате `YYYY-MM-DD` (`date +%F`) — она
   понадобится и здесь, и в §4.
2. Получи список файлов в корне репозитория: `mcp__github__get_file_contents`
   (`owner: "andrei0783-prog"`, `repo: "tracker-data"`, `path: "/"`).
3. Из списка оставь только файлы с именем вида `YYYY-MM-DD.json` (отбрось
   `README.md`, каталог `test/` и всё остальное) и **строго старше
   сегодняшней даты** — сегодняшний файл в кандидаты не берётся, даже если
   он уже существует (например, из более раннего прогона за сегодня же).
4. Если таких файлов нет — прошлых прогонов нет, это первый запуск.
   Пропусти §3 (сравнивать не с чем) и переходи сразу к §4.
5. Если такие файлы есть, возьми файл с максимальной (самой поздней) датой
   среди оставшихся и прочитай его: `mcp__github__get_file_contents`
   (`path: "<эта дата>.json"`). Это и есть предыдущий прогон — JSON-массив
   в том же формате, что и текущий (§1).

### 3. Посчитай diff и примени правила значимости

Пропусти этот раздел целиком, если предыдущего прогона нет (§2, шаг 4).

Правила значимости живут в `KNOWLEDGE.md` в корне проекта — прочитай этот
файл (`Read`) и следуй ему буквально, не выдумывай собственный порог или
трактовку скидки/рассрочки. Кратко: сравнивается эффективная цена
(`sale_price`, если не `null`, иначе `regular_price`); значимо изменение
эффективной цены на ≥ 1%, а также появление/исчезновение скидки, рассрочки,
самой цены (`null` ↔ число) и появление/пропажа товара в списке — независимо
от порога. Товары сопоставляются по точному URL.

1. Сопоставь товары текущего и предыдущего прогона по полю `url`.
2. Для каждой пары (и для товаров без пары — новых или пропавших) реши по
   `KNOWLEDGE.md`, значимо ли изменение.
3. Собери итоговый список значимых изменений — только те товары, где
   сработало хотя бы одно правило из `KNOWLEDGE.md`. Для каждого укажи
   товар, что именно изменилось и значения «было → стало».
4. Товары без значимых изменений в этот список не включай — это и есть
   отличие от «сырых цен целиком».

### 4. Сохрани прогон в tracker-data

Каждый прогон — отдельный файл `YYYY-MM-DD.json` (дата прогона) в корне
приватного репозитория `andrei0783-prog/tracker-data`, ветка `main`. Запись
идёт напрямую через GitHub MCP — не клонируй репозиторий локально и не
делай `git push`, каждый вызов MCP на запись файла сам создаёт коммит.

1. Узнай сегодняшнюю дату в формате `YYYY-MM-DD` (например, `date +%F`) и
   используй её как имя файла `<дата>.json`.
2. Проверь, существует ли уже файл `<дата>.json` в репозитории — вызови
   `mcp__github__get_file_contents` (`owner: "andrei0783-prog"`,
   `repo: "tracker-data"`, `path: "<дата>.json"`). Если трекер уже
   запускали сегодня, файл найдётся — запомни его `sha`. Если получена
   ошибка "не найдено" — файла ещё нет, `sha` передавать не нужно.
3. Запиши файл вызовом `mcp__github__create_or_update_file`:
   - `owner: "andrei0783-prog"`, `repo: "tracker-data"`;
   - `path: "<дата>.json"`, `branch: "main"`;
   - `content` — массив прогона из §1 как есть (валидный JSON);
   - `message` — короткое сообщение коммита, например
     `Прогон трекера за <дата>`;
   - `sha` — только если файл на этот день уже существовал (шаг 2); при
     первом прогоне за день это поле не передавай.
4. Если прогон за сегодня уже был, повторный запуск в тот же день
   перезаписывает файл этого дня (а не создаёт второй) — так на дату
   всегда приходится ровно один файл.

### 5. Покажи результат

- **Если предыдущего прогона не было (§2, шаг 4):** сравнивать не с чем.
  Покажи массив прогона из §1 как таблицу — по одной строке на товар,
  столбцы: товар, URL, `regular_price`, `sale_price`, `has_credit` — и
  отметь, что это первый прогон и он стал точкой отсчёта.
- **Если предыдущий прогон был:** не показывай сырую таблицу цен. Покажи
  только список значимых изменений из §3 — по одному пункту на товар, с
  указанием, что изменилось, и значений «было → стало». Если список пуст,
  так и скажи: значимых изменений нет, все цены и условия — в пределах
  правил `KNOWLEDGE.md`.

## Проверка перед ответом

- Массив прогона из §1 содержит ровно столько объектов, сколько URL в
  зашитом списке — ни один товар не пропущен, порядок совпадает со списком.
- Для каждого товара учтены все три поля из `extract-price`, без пересчёта
  и переинтерпретации.
- Товары, для которых `extract-price` не смог найти цену, всё равно
  присутствуют в массиве прогона со значениями `null`/`false`, а не молча
  выброшены.
- Предыдущий прогон искался **до** сохранения нового и среди файлов
  строго старше сегодняшней даты (§2).
- Diff (§3) построен по правилам из `KNOWLEDGE.md`, а не по придуманным на
  ходу порогам, и включает только товары со значимыми изменениями.
- Файл `<дата>.json` записан в `tracker-data` (создан или обновлён) с тем
  же массивом, что использовался для diff, и в ответе показана ссылка на
  коммит из результата MCP-вызова.
- Ответ пользователю показывает diff (или отметку о первом прогоне), а не
  сырую таблицу цен целиком, если предыдущий прогон был.
